Com base na análise completa do projeto, elejo 3 temas prioritários em ordem de importância:

🔴 1. Segurança — Server API sem proteção server-side
As rotas /api/sync/matches, /api/sync/results e /api/sync/teams só são protegidas pelo middleware client-side (is-admin). Qualquer pessoa com uma sessão válida pode chamar essas rotas diretamente via curl ou Postman e importar/sobrescrever dados no banco. A proteção precisa existir no servidor também.

🟡 2. UX — alert() nativo em 

palpites.vue
O feedback de sucesso/erro ao salvar palpites usa alert() do browser — aquele popup feio. O projeto tem um sistema de design premium e isso poluí a experiência. Merece um toast/notificação in-app.

🟠 3. Type safety — 

(supabase as any)
 em 

useBets.ts
O upsert de palpites usa um cast 

(supabase as any)
 para contornar o TypeScript. Isso desliga a proteção de tipos justamente numa operação crítica de escrita no banco.

Na minha opinião, o ponto 1 é o mais urgente — é uma falha de segurança real, não cosmética. Os outros dois são qualidade de código/UX.

⚠️ Pontos de Atenção
app/standings.get — Esta é a rota mais perigosa. Ela é chamada toda vez que alguém carrega a tela de classificação. Em produção com 10 usuários cada um carregando a página 5 vezes, seriam 50 requisições — mas como tem limite de 10/min, pode haver erros 429 Too Many Requests.
sync/results.post — Se um CRON automático rodar a cada minuto, seriam 1 chamada/minuto, dentro do limite.
✅ Consumo Estimado em Desenvolvimento
Cenário	Chamadas/dia estimadas
Dev solo (você testando)	~20-50 requisições
Com CRON a cada 5min	+288/dia
Standings sem cache	+variável por page load
Veredicto: Para desenvolvimento, o consumo está dentro do esperado e seguro. O limite de 10 req/min é confortável para 1 desenvolvedor.
